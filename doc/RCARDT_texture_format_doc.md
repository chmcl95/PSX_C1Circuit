# RCARDT テクスチャフォーマット仕様書（`00000001`）

対象: PS1レースゲーム「C1 Circuit」(SLPS-00279) の車体テクスチャ `RCARDT/*/00000001`

市販版ディスクの全15車種を解析し、**ブロックがファイル末尾までちょうど並ぶこと**
（余りバイト0）を全ファイルで確認したうえでまとめた仕様書です。

モデルファイル `00000000` の仕様は
[RCARDT_format_doc.md](RCARDT_format_doc.md) を参照。

---

## 1. 全体レイアウト

ヘッダーもターミネータも無く、**VRAM転送ブロックがひたすら並ぶだけ**の形式。
パレット（CLUT）ブロックとピクセル（PXL）ブロックが**厳密に交互**に並ぶ。

```
VramBlock  clut[0]     // パレット
VramBlock  pixels[0]   // ピクセル
VramBlock  clut[1]
VramBlock  pixels[1]
...
```

- **格納順 = VRAMへの転送順。** 後のブロックが先のブロックを上書きする
- 全15車種でブロック数は偶数、かつ偶数番目が必ずパレット・奇数番目が必ずピクセル
- ファイルサイズは `Σ(12 + size)` と厳密に一致する（パディングなし）

### 検証結果

| 車種 | サイズ | テクスチャ数 | 車種 | サイズ | テクスチャ数 |
|---|---|---|---|---|---|
| AE86 | 25,224 | 15 | R32R | 28,872 | 15 |
| AE92 | 27,208 | 15 | R33R | 26,744 | 13 |
| EG6 | 29,168 | 10 | RPS13 | 30,696 | 11 |
| FC3S | 19,840 | 16 | S13 | 24,024 | 13 |
| FD3S | 29,632 | 12 | S14 | 31,224 | 13 |
| HCR32 | 27,464 | 15 | SW20 | 28,720 | 10 |
| JZA70 | 18,896 | 14 | Z32 | 23,688 | 15 |
| JZA80 | 29,448 | 15 | | | |

## 2. VramBlock 構造体（12 bytes ヘッダー + ペイロード, リトルエンディアン）

| オフセット | サイズ | 型 | フィールド | 説明 |
|---|---|---|---|---|
| 0x00 | 4 | uint32 | `size` | ペイロードのバイト数。**常に `width × height × 2`** |
| 0x04 | 2 | uint16 | `vramX` | VRAM上の転送先X座標 |
| 0x06 | 2 | uint16 | `vramY` | VRAM上の転送先Y座標 |
| 0x08 | 2 | uint16 | `width` | **16bitワード単位**の幅 |
| 0x0A | 2 | uint16 | `height` | 走査線数 |
| 0x0C | size | byte[] | payload | パレットまたはピクセルデータ |

パレットブロックとピクセルブロックは**同一構造**であり、区別は用途のみ。

> **旧解釈との対応**
> 従来「テクスチャヘッダー 0x08 = 不明（実例では 0x0010）／0x0A = パレット個数」
> とされていたものは、それぞれ `width`（パレットは16色なので常に16）と
> `height`（＝パレット枚数）である。同様に「0x00 = パレット総サイズ
> （オフセットの可能性あり）」は `size` そのもの（オフセットではない）。
> これで両ヘッダーの全フィールドが確定した。

### パレットブロック

- `width` は **常に 16**（4bpp = 16色 × 2バイト = 32バイト/パレット）
- `height` は **パレット枚数**。市販版では1〜6（NA8Cはボディカラー違いで5枚）
- 転送先はVRAM左下のCLUT領域。市販版では `vramX = 128` 固定

### ピクセルブロック

- `width` は16bitワード単位。**4bppでは1ワード = 4ピクセル**なので
  **実ピクセル幅 = `width × 4`**
- `height` はそのままピクセル高さ
- 実測サイズ範囲: 8×8 〜 256×102

## 3. 色・パレット

- **4BPP（16色）固定**
- 1色 = 2バイト **BGR555**。ビット構成（MSB→LSB）:
  `STP(半透明)フラグ 1bit | B 5bit | G 5bit | R 5bit`
- 例: `1F 00` (=0x001F) → 赤 / `E0 03` (=0x03E0) → 緑 / `00 7C` (=0x7C00) → 青
- **アルファ値は存在しない**。半透明はSTPフラグ（`色 + 0x8000`）で表現する

### 既知のパレットVRAM座標

| 用途 | 座標 | 市販版での確認 |
|---|---|---|
| 車ボディ | (128, **496**) | 全車種 |
| 半透明・影 | (128, **503**) | 全車種 |
| タイヤ（停止） | (128, **504**) | 全車種 |
| タイヤ（回転ブラー） | (128, 507) | 一部車種 |

その他 497〜511 も車種により使用される。

### CLUT X の「÷16」

モデル側（`00000000`）の `clut.x_coordinate` は **VRAM X ÷ 16** を格納する。
テクスチャ側（`00000001`）の `vramX` は **VRAM X そのもの**。

```
パレットを VRAM (128, 503) に置く場合
  00000001.BIN : vramX = 128, vramY = 503
  00000000.BIN : clut_x = 8   (=128/16), clut_y = 503
```

この二重指定を人手でやると必ず食い違うため、`C1CircuitTool rcardt-unpack` が
生成する `clut_presets.json` に一度だけ書き、両ツールがそこから導出する
（§6参照）。

## 4. VRAM配置ルール

- **プレイヤーカーのテクスチャ領域: X = 640〜703, Y = 0〜256**
- **X = 704 (0x2C0) 以降はライバルカー領域**。書き込むと他車が壊れる
- X座標はピクセル数と一致しない（VRAMは16bit/word、4bppでは1word=4px）

### 「亡霊」現象

改造テクスチャがバニラより小さい／配置がズレていると、上書きされなかった
VRAM領域に前のテクスチャが残り続ける。ピクセルブロックの `vramX/vramY` と
サイズを正しく設定し、対象領域を完全に塗り潰すこと。

## 5. TIM / CLT / PXL との関係

**VramBlock は Sony TIM の「データセクション」と、長さフィールドの数え方だけが
異なる。**

```
TIM/CLT/PXL : uint32 bnum (= ペイロード + 12), uint16 dx, dy, w, h, ペイロード
C1 の BIN    : uint32 size (= ペイロード)      , uint16 dx, dy, w, h, ペイロード
```

つまり相互変換は **`±12` と 8バイトのファイルヘッダーの有無だけ**。

| 形式 | ファイルID (0x00) | Flags (0x04) | 内容 |
|---|---|---|---|
| TIM | 0x10 | `0x00000008`（4bpp + CLUT有り） | CLUTセクション + ピクセルセクション |
| CLT | 0x11 | `0x00000002`（16bpp） | CLUTセクションのみ |
| PXL | 0x12 | `0x00000000`（4bpp） | ピクセルセクションのみ |

> ID は仕様書上 11h=PXL / 12h=CLT だが、**実ゲームおよび ps-image は
> 11h=CLT / 12h=PXL** で運用されている。

### 手作業での変換（バイナリエディタ）

```
パレットデータのCLT化:
  先頭に  11 00 00 00 02 00 00 00  （8バイト）を付与
  size を 0xC 加算した値に書き換え

ピクセルデータのPXL化:
  先頭に  12 00 00 00 00 00 00 00  （8バイト）を付与
  size を 0xC 加算した値に書き換え
```

### ツールでの変換

`C1CircuitTool rcardt-unpack` / `rcardt-pack` が
**CLUT+ピクセルのペア ⇄ TIM 1ファイル**を自動変換する。TIMなら ps-image で
パレットとピクセルを同時に編集できる。全15車種で
`rcardt-unpack → rcardt-pack` がバイト単位で一致することを確認済み。

> ps-image は **VRAM座標を編集できない**。そのため `rcardt-pack` は
> TIM内の座標を無視し、`clut_presets.json` の値を正としてVRAM座標を書き込む。

## 6. `clut_presets.json`

`rcardt-unpack` が車種ごとに生成する、テクスチャとVRAM配置の対応表。
`rcardt-pack` と Blenderアドオンが同じファイルを読む。

```json
{
  "version": 1,
  "presets": [
    {
      "name": "000_body_256x64",
      "file": "000_body_256x64.TIM",
      "clut_x": 128,
      "clut_y": 496,
      "pixel_x": 640,
      "pixel_y": 0,
      "note": "1 palette(s), 256x64 px 4bpp"
    }
  ]
}
```

| フィールド | 意味 |
|---|---|
| `name` | スロット名。Blenderのマテリアルで選択する識別子 |
| `file` | 対応するTIMファイル名 |
| `clut_x` / `clut_y` | パレットのVRAM座標。モデル側には `clut_x / 16` が書かれる |
| `pixel_x` / `pixel_y` | ピクセルデータのVRAM座標 |

- **配列の順序 = VRAM転送順**（後のものが先のものを上書きする）
- ピクセルの幅・高さはTIM側から取るため、ps-imageで画像サイズを変えても
  このファイルの編集は不要
- `clut_x` は16の倍数でなければならない（モデル側が ÷16 でしか保持できないため）

## 7. 半透明（影・ヘッドライト）の成立条件

以下3つを**すべて**満たす必要がある:

1. モデル側の描画コマンドで **Semi-Transparent** を有効化
   （アドオンの RCARDT Material Editor → GPU Command Flags）
2. パレット側の **STPフラグを有効化**（該当色に `0x8000` を加算）
3. **ピクセルデータが黒 (0,0,0) 以外**であること

加えてモデル側で、該当パレットのVRAM座標を CLUT スロットで指定し、
UVを該当パレットが適用されるテクスチャ位置に合わせる。

### 制約

- **半透明面に2色以上使えない。** 最後に格納されたテクスチャのパレット色に
  引っ張られる
- 回避策: マテリアルの **Texture Disable** でテクスチャを無視し、
  マテリアルカラーで着色すると複数色を使える

## 8. `.S` アーカイブと LZSS0

`00000001.BIN` は `.S` アーカイブの2番目のエントリとして LZSS0 圧縮されている。

```
ヘッダー:
  uint32   : 格納ファイル個数
  uint32[] : ファイル毎のサイズ（4バイト境界パディング込み）

各エントリ:
  uint32   : 展開後のサイズ
  byte[]   : LZSS0圧縮データ（サイズ - 4 バイト）
```

### LZSS0 の辞書初期化（重要）

Okumura式 LZSS そのもの:

- リングバッファ **4096バイト**、**0x00で初期化**
- 書き込みカーソルの初期位置は **N - F = 4078**（0ではない）
- 最長一致 F = 18、閾値 THRESHOLD = 2

**この初期化を誤ると、圧縮データが初期辞書（＝ゼロ領域）を参照している
箇所だけが壊れる。** モデルファイルは初期辞書をほぼ参照しないため正常に
見えるが、テクスチャファイルは参照するため破損する。実際
`AuroraLib.Compression 2.0.0` はこの規約が異なり、市販版17アーカイブ中
**16のテクスチャが黙って壊れていた**（差分は全て「正=0x00 / 誤=ゴミ」、
位置は全てファイル先頭から 0x1000＝ウィンドウ1個分以内）。

なお圧縮側はこの問題の影響を受けない（エンコーダが初期辞書を参照する
必要がないため）。
