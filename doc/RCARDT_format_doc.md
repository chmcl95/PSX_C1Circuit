# RCARDT モデルフォーマット仕様書（`00000000`）

対象: PS1レースゲーム「C1 Circuit」系タイトルの車体モデルファイル `RCARDT/*/00000000`

本ドキュメントは `c1circuit_rcardt_model.bt`（010 Editor Binary Template）の定義を
Pythonで実装し、**市販版ディスクの全15車種**（`RCARDT/*.S` から展開した
`00000000.BIN`）に対して **バイト単位のラウンドトリップ完全一致** を確認したうえで
まとめた仕様書です。

テクスチャファイル `00000001` の仕様は
[RCARDT_texture_format_doc.md](RCARDT_texture_format_doc.md) を参照。

---

## 1. 全体レイアウト

```
Node   nodes[4]                                  // 32 bytes ×4 = 128 bytes
Surface[nodes[0].surfaceLength]  (node 0 の面データ)
Surface[nodes[1].surfaceLength]  (node 1 の面データ)
Surface[nodes[2].surfaceLength]  (node 2 の面データ)
Surface[nodes[3].surfaceLength]  (node 3 の面データ)
```

- ファイル先頭に **4個固定** の `Node` ヘッダー（各32byte、計128byte）が並ぶ
- その後ろに、各Nodeの `surfaceLength` で示された枚数分の `Surface`（各60byte）が
  Node0→Node1→Node2→Node3の順に連続して並ぶ
- ファイル全体のサイズは理論上 `128 + Σ(surfaceLength_i × 60)` と一致する
  （検証したサンプルのうち `06_SW20` のみ末尾に無関係なゼロ埋め60byteの
  パディングが付加されていたが、これは本フォーマットの一部ではない）

### 検証結果（ラウンドトリップ）

市販版15車種すべてについて、`unpack → pack` が **バイト単位で完全一致**
（`ptr_mdl`・末尾パディングを含む）:

| 車種 | サイズ | Node面数 | マテリアル数 | 車種 | サイズ | Node面数 | マテリアル数 |
|---|---|---|---|---|---|---|---|
| AE86 | 14,588 | 177/16/16/32 | 7 | R32R | 13,208 | 154/16/16/32 | 10 |
| AE92 | 15,548 | 193/16/16/32 | 5 | R33R | 13,388 | 157/16/16/32 | 7 |
| EG6 | 13,028 | 151/16/16/32 | 7 | RPS13 | 12,488 | 142/16/16/32 | 6 |
| FC3S | 12,908 | 149/16/16/32 | 7 | S13 | 13,928 | 166/16/16/32 | 8 |
| FD3S | 14,648 | 178/16/16/32 | 4 | S14 | 12,848 | 148/16/16/32 | 5 |
| HCR32 | 12,968 | 150/16/16/32 | 9 | SW20 | 13,748 | 163/15/16/32 | 7 |
| JZA70 | 12,728 | 146/16/16/32 | 6 | Z32 | 11,888 | 132/16/16/32 | 8 |
| JZA80 | 13,928 | 166/16/16/32 | 5 | | | | |

「マテリアル数」は GPU ステート（色・コマンドフラグ・CLUT・TexPage）が
一致する面をまとめた場合の実数。面法線を含めて数えると面数とほぼ同数（FD3Sで216）に
膨れ上がるため、§4-4 のとおり法線は面ごとの派生値として扱う必要がある。

`ptr_mdl` はランタイム専用ポインタのため新規作成時は0でよいが、
インポート時は保持する（§5-3）。

## 2. Node 構造体（32 bytes, リトルエンディアン）

| オフセット | サイズ | 型 | フィールド名 | 説明 |
|---|---|---|---|---|
| 0x00 | 4 | int32 | `surfaceLength` | このNodeが持つSurfaceの枚数 |
| 0x04 | 12 | int32×3 | `position[3]` | Nodeの位置オフセット（X, Y, Z / 整数単位） |
| 0x10 | 12 | int32×3 | `rotation[3]` | Nodeの回転（X, Y, Z / 詳細は §5 参照） |
| 0x1C | 4 | uint32 | `ptr_mdl` | **ランタイム専用ポインタ**。ファイル上の値は意味を持たず、
  ロード時にゲームが実行時アドレスへ上書きする。エクスポート時は常に`0`でよい |

### 4つのNodeの役割（確定・実機挙動で確認済み）

5台分のサンプルデータから見出したパターンを、**実際のゲーム内挙動と照合し一致を確認済み**:

| Node | 役割（確定） | 位置の傾向 |
|---|---|---|
| Node 0 | 車体本体（ボディシェル） | 常に `(0, 0, 0)` （基準点） |
| Node 1 | 前輪・右側 | X: 正（+82〜+89）, Y: 負（-28〜-30、本体中心より下）, Z: 負（-134〜-151、前方） |
| Node 2 | 前輪・左側 | X: 負（-81〜-88、Node1とほぼX対称）, Y・Zはほぼ同値 |
| Node 3 | 後輪（左右セット） | Z: 正（+130〜+155、後方）。`surfaceLength` がNode1/2のちょうど2倍
  （例: Node1/2が16面ならNode3は32面）で、**左右の後輪ジオメトリを
  1つのNodeにまとめて格納している**（後輪はステアリングしないため単一Node） |

`rotation` は全サンプルで `(0, 0, 0)` のみ確認されており、実データからは
角度エンコーディングの検証ができていない（§5参照）。

## 3. Surface 構造体（60 bytes, リトルエンディアン）

PS1 GPUのテクスチャ付きポリゴン描画パケット（POLY_FT4 / POLY_FT3相当）に対応する。

| オフセット | サイズ | 型 | フィールド名 | 説明 |
|---|---|---|---|---|
| 0x00 | 3 | uint8×3 | `color[3]` | サーフェス単位の単色（R, G, B / 0-255）。
  **頂点ごとではなく面ごとに1色のみ** 保持する |
| 0x03 | 1 | uint8 | `command` | ビットフィールド。§4-1参照 |
| 0x04 | 2 | uint8×2 | `uv0` | 頂点0のテクスチャ座標 (u, v) |
| 0x06 | 2 | uint16 | `clut` | ビットフィールド。§4-2参照 |
| 0x08 | 2 | uint8×2 | `uv1` | 頂点1のテクスチャ座標 |
| 0x0A | 2 | uint16 | `texpage` | ビットフィールド。§4-3参照 |
| 0x0C | 2 | uint8×2 | `uv2` | 頂点2のテクスチャ座標 |
| 0x0E | 2 | uint8×2 | `uv3` | 頂点3のテクスチャ座標 |
| 0x10 | 32 | Vertex×4 | `position[4]` | 頂点座標×4（各8byte、下記参照） |
| 0x30 | 12 | int32×3 | `normal[3]` | **面法線**（非正規化）。§4-4参照 |

**Vertex（8 bytes）**

| オフセット | サイズ | 型 | フィールド | 説明 |
|---|---|---|---|---|
| +0x00 | 2 | int16 | `x` | ローカル座標X |
| +0x02 | 2 | int16 | `y` | ローカル座標Y |
| +0x04 | 2 | int16 | `z` | ローカル座標Z |
| +0x06 | 2 | int16 | `padding` | 未使用（常に0） |

### 頂点順序（重要）

`position[4]` はBlenderの一般的な面の頂点順（ファン順: v0→v1→v2→v3）ではなく、
**PS1 GPUの三角形ストリップ順**で格納されている。四角形ポリゴンは
`(v0, v1, v3)` と `(v1, v3, v2)` の2枚の三角形として描画される。

- 三角形ポリゴン（`_quad`ビット=0）の場合、4頂点目は3頂点目の複製が入る
- ワインディング順（表裏判定）は、格納順の2番目・3番目要素を入れ替えることで
  一括反転できる（本アドオンの `Flip Winding` オプションで確認済み）

## 4. ビットフィールド仕様

### 4-1. `command`（1 byte）

| bit | フィールド | 説明 |
|---|---|---|
| 0 | `raw_texture` | 1=ライティング/シェーディングを無視し生テクスチャ色を使用 |
| 1 | `semi_transparent` | 1=半透明合成を有効化 |
| 2 | `textured` | 1=テクスチャ有効 |
| 3 | `is_quad` | 1=四角形（4頂点）, 0=三角形（3頂点＋複製） |
| 4 | `gouraud` | 1=グーローシェーディング（ただし本フォーマットは面単位1色のみ保持） |
| 5-7 | `render_type` | 1=ポリゴン, 2=ライン, 3=矩形（本フォーマットでは常に1=ポリゴン想定） |

実データ例: `command = 44 (0x2C)` → `textured=1, is_quad=1, gouraud=0,
render_type=1`（他ビットは0）。これはテクスチャ付き四角ポリゴンとして一貫している。

### 4-2. `clut`（uint16）— カラールックアップテーブル位置

| bit | フィールド | 説明 |
|---|---|---|
| 0-5 | `x_coordinate` | 実際のVRAM X座標 = 値 × 16 |
| 6-14 | `y_coordinate` | VRAM Y座標（そのまま、0-511） |
| 15 | (unused) | 未使用 |

実データ例: `clut = 32072 (0x7D48)` → `x_coordinate=8`（VRAM X=128）,
`y_coordinate=501`。PS1のVRAM座標として妥当な範囲。

### 4-3. `texpage`（uint16）— テクスチャページ位置

| bit | フィールド | 説明 |
|---|---|---|
| 0-3 | `texpage_x` | 実際のVRAM X座標 = 値 × 64 |
| 4 | `texpage_y` | 実際のVRAM Y座標 = 値 × 256 |
| 5-6 | `semi_transparency_mode` | 0: B/2+F/2, 1: B+F（加算）, 2: B-F（減算）, 3: B+F/4 |
| 7-8 | `texture_page_colors` | 0: 4bit(CLUT), 1: 8bit(CLUT), 2: 15bit, 3: 予約 |
| 9-10 | (未解明) | 用途不明の2bit |
| 11 | `texture_disable` | 1=テクスチャ無効化 |
| 12-15 | (未解明) | 用途不明の4bit |

実データ例: `texpage = 10 (0x000A)` → `texpage_x=10`（VRAM X=640）,
`texpage_y=0, semi_transparency_mode=0, texture_page_colors=0`
（4bit CLUTモード。CLUTフィールドが存在することと整合する）。

### 4-4. `normal[3]`（int32×3）— 面法線【解明済み】

従来「未解析12バイト（`Unknown Tail (0x2C)`）」「uint16×6」とされていたフィールド。
実体は **int32×3 の非正規化面法線** で、値は格納順の頂点から求めた外積そのもの:

```
normal = cross(position[1] - position[0], position[2] - position[0])
```

**検証**: 市販版 15車種・全3,341面（AE86 241, AE92 257, EG6 215, FC3S 213,
FD3S 242, HCR32 214, JZA70 210, JZA80 230, R32R 218, R33R 221, RPS13 206,
S13 230, S14 212, SW20 226, Z32 196）で **1面の例外もなく上式と完全一致**。

このため本フォーマットにおいて `normal` は **ジオメトリから一意に決まる派生データ**であり、
手入力する意味を持たない。エクスポータは常に頂点座標から再計算する。

> **描画順パラメータではない。**
> 「タイヤ内側パーツがホイールより手前に描画される」問題の原因として
> このフィールドが疑われていたが、外積そのものである以上、値を変えても
> ソート順には影響しない（変えれば法線が誤りになるだけ）。描画順の制御要因は
> 別にあると考えられる。

**例外**: メニュー用（`ALLCAR.S`）モデルから変換された `HK11` 改造版では、
211面中210面で法線が上式と一致しない。頂点を1/2にスケールした際に法線が
そのまま残されたためで（比率がおおむね×4）、市販版RCARDTデータには
この状態のものは存在しない。インポータはこの不一致を検出して警告する。

## 5. 未確定・要検証の項目

以下はバイナリのフィールド位置・サイズは確定しているが、**値の意味/単位**が
実データのみからは断定できない項目:

- **`rotation[3]`（Node）の角度単位** — 実サンプル全てで `(0,0,0)` のみ観測されて
  おり、他の値のサンプルが無いため単位を実証できていない。本アドオンでは
  PS1で一般的な12bit角度表現（0-4095 = 0-360°）と仮定して実装している
- **`texpage` bit9-10, bit12-15** — 用途不明。本アドオンでは
  `unk_bit9` / `unk_bit12` として生の値をそのまま出力できるようにしてある
- **座標スケール** — ゲーム内の1整数単位が実世界のどの長さに対応するかは
  未実証（本アドオンでは車体寸法から1units=1cm相当と仮定し、デフォルト
  `Position Scale=100` としている）
- **描画順の制御方法** — Node Index順（0が最優先）以外の制御手段は未発見

## 5-1. 三角形面について

市販版15車種 **3,341面すべてが四角形**（`is_quad = 1`）であり、三角形面は
1枚も存在しない。ゲームは全サーフェスに四角形の描画コマンドを発行するため、
三角形を混ぜると描画が破綻する。

`command` の `is_quad` ビットは三角形（0）も表現できるが、これは
PS1 GPUパケットの汎用フィールドであり、本ゲームがそれを解釈する証拠は無い。
5角形以上は60バイトのパケットに収まらないため、そもそも表現できない。

`io_export_rcardt` は四角形以外の面があるとエクスポートを中断する
（`Non-Quad Faces` オプションで意図的に書き出すことも可能）。

## 5-2. メニュー用（ALLCAR）レイアウトとの違い

メニュー用モデルは **ノードヘッダー128バイトのうち先頭4バイト（＝面数）だけ**を
持ち、残り124バイトが存在しない:

```
レース用 (RCARDT) : Node[4] (128 byte) + Surface[Σ surfaceLength]
メニュー用 (ALLCAR): uint32 surfaceCount (4 byte) + Surface[surfaceCount]
```

市販版の `RCARDT/HK11.S`（没マーチ）の `00000000.BIN` は **12,664 = 4 + 211×60** で
このメニュー用レイアウトのまま格納されており、レース用として読み込めない。
修正版は 124バイトを補い **12,788 = 128 + 211×60** となっている。

## 5-3. `ptr_mdl` の扱い

ランタイム専用ポインタで、市販版には PSX RAM アドレスの残骸
（`0x291B8942` など）が入っている。ゲームはロード時に上書きするため
新規作成時は `0` でよいが、インポート時は保持しておくと元ファイルと
バイト単位で一致する再エクスポートが可能になる。

## 5-4. 末尾パディング

市販版 `SW20` は最終サーフェスの後ろに60バイトのゼロ埋めを持つ。
フォーマットの一部ではないが、保持しないとインポート→エクスポートで
ファイルが変化する。

## 6. 座標系・エクスポート時の変換（アドオン実装メモ）

`io_export_rcardt` アドオンでは、実機での動作確認により以下を**常時固定**で適用する:

1. 頂点座標・Node位置の両方に **X軸+90度回転** を適用
   （Blender上のモデルの向きとゲーム内での向きが一致することを確認済み）
2. 四角形は Blenderのファン順 `(v0,v1,v2,v3)` → PS1ストリップ順
   `(v0,v1,v3,v2)` に並べ替え（`Reorder Quad Vertices` オプション、既定ON）
3. ワインディング順は `Flip Winding` オプションで一括反転可能
4. UV座標は0-1の正規化値を0-255のバイト値に変換（`Flip V` オプションでV反転、既定ON）

インポート時はこれらすべての**厳密な逆変換**を適用する。市販版15車種について
「インポート → エクスポート」がバイト単位で一致することを Blender 4.3.2 上で
確認済み（既定オプションのまま）。
